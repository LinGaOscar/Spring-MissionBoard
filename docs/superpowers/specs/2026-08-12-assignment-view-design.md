# 人員派工分頁 設計文件

## 背景與範圍

任務導向重構時（`docs/superpowers/specs/2026-08-08-missionboard-task-oriented-rewrite-design.md`），舊的樹編輯器／人員派工／甘特三個分頁因資料模型改變被整個移除，列為後續依新模型各自重做。人員派工分頁在移除前其實只是個 placeholder（`<p class="placeholder-tab">人員派工檢視開發中</p>`），從未真正實作過，這次是全新設計，沒有舊邏輯可沿用。

這是三個待補功能中的第二個（分類管理畫面 → **人員派工分頁** → 甘特分頁，依序各自成一份 spec／plan／實作循環）。本規格只涵蓋人員派工分頁。

**不改動後端**：`PATCH /api/projects/{id}/tasks/{taskId}/assignee` 已存在且已驗證指派對象須為專案成員、支援 `assigneeId: null`（清空指派），純前端功能。

**目的**：同時滿足「工作量總覽」（一眼看出每個成員手上有哪些任務）與「重新指派」（拖曳調整）兩個需求。

## 分頁結構調整

目前專案詳情頁根元件（`project-detail.js` 結尾的 `createApp`）是空殼，直接掛 `kanban-view`，沒有 tab 切換。本次改為雙分頁：

- 根元件加 `activeTab`（預設 `'kanban'`），畫面上方兩顆按鈕切換 `看板` / `人員派工`
- 用 **`v-if`**（不是舊版的 `v-show`）切換兩個分頁元件。原因：兩個分頁各自獨立 fetch 一份 `tasks`，若用 `v-show` 讓兩個元件同時常駐掛載，會出現「在看板拖曳改了狀態，人員派工分頁看到的還是舊資料」的不同步問題。`v-if` 犧牲「顯示已完成」開關在切分頁時的記憶（見下），換取分頁一定拿到新資料，是這次範圍下最低成本的正確做法。

## UI 位置與畫面結構

新增 Vue 元件 `AssignmentView`，與 `KanbanView` 平行、各自獨立管理自己的 `tasks`/`categories`/`members` 狀態。

- 依成員分欄、橫向捲動，最左側固定「未指派」欄，其餘依 `GET /api/projects/{id}/members` 回傳順序各一欄
- 每欄標頭：成員姓名 + 任務數（依當前篩選後的計數，見下方「顯示已完成」開關）
- 卡片內容：標題、狀態小標籤（未開始/進行中；`DONE` 只在開關開啟時才會出現在欄位裡，故卡片上仍可標示以區分未開始/進行中）、到期日（沿用看板既有 `overdue` 樣式與 `isOverdue` 判斷邏輯）、優先度色條（沿用 `priority-*` class）
- 卡片**不含分類資訊**，保持精簡；需要看分類回看板分頁
- 頁面右上角一個開關「顯示已完成」，預設關閉，影響本分頁所有欄位的過濾。不持久化：切到看板分頁再切回來（`v-if` remount）會重置為關閉

## 互動

- 拖曳卡片跨欄＝呼叫 `PATCH .../tasks/{taskId}/assignee`（目標欄是「未指派」則傳 `assigneeId: null`）
- 本地樂觀更新：同時改 `assigneeId` **與** `assigneeDisplayName`（不只改 id，否則欄位分組會找不到對應成員），沿用被移除版本 `updateAssignee` 的既有模式；失敗回滾＋`showToast`
- `canWrite === false`（唯讀角色／封存專案）時卡片 `draggable` 關閉，僅供瀏覽，沿用看板既有 pattern
- 欄內排序：**固定規則排序，不使用 `sort_order`、不呼叫 `move` 端點**。規則：依 `dueDate` 升冪，無到期日排最後；到期日相同（含都無到期日）時依任務 `id` 升冪，穩定排序不需額外欄位
- 卡片**不可點擊開 modal**（v1 範圍明確排除）。原因：看板的編輯 modal（`modal.form`／`saveTask`／`queueTaskWrite`）目前整段寫在 `KanbanView` 內部，人員派工分頁若要借用得複製一份邏輯（違反專案慣例）或拆共用元件（中型重構，超出這次範圍）。「總覽＋改指派」兩個目的已經由「分欄＋拖曳」滿足，完整編輯（標題/分類/優先度/日期）回看板分頁做

## 資料流與 API 使用

**載入**（`mounted()`，`v-if` 每次切回都會重新觸發）：
- `GET /api/projects/{id}/tasks`
- `GET /api/projects/{id}/members`

不需要 `categories`（卡片不顯示分類）。

**改指派**：`PATCH /api/projects/{id}/tasks/{taskId}/assignee`，body `{assigneeId}`（`null` 表示清空指派），沿用既有 `TaskController`/`TaskService.updateAssignee`，無需改動。

## 錯誤處理

- 沿用既有 `api()` 骨架（CSRF、網路錯誤攔截、`showToast`）
- 拖曳失敗（理論上只會是後端在極少數 race condition 下拒絕，例如指派瞬間該成員被移出專案）：回滾 `assigneeId`/`assigneeDisplayName` 到拖曳前的值＋toast 錯誤訊息，不整頁重抓

## 測試重點

本次不改後端，`TaskController`/`TaskService` 既有測試（含 `updateAssignee` 的成員驗證）維持不動、不需新增。

前端沒有自動化測試框架（`find` 確認 repo 內無 `package.json`/`*.test.js`），驗證方式是實際啟動應用程式、瀏覽器操作一輪並截圖存證：
- 分頁切換（看板 ↔ 人員派工），確認雙向資料一致（在看板改指派，切到人員派工分頁看得到最新結果；反之亦然）
- 拖曳任務卡片到不同成員欄位，確認後端已寫入（重新整理後仍在新欄位）
- 拖曳任務卡片到「未指派」欄位，確認 `assigneeId` 清空
- 唯讀角色（如 `PROJECT_MEMBER` 非任務相關人／封存專案）卡片不可拖曳
- 「顯示已完成」開關切換，確認 `DONE` 任務正確隱藏/顯示，欄位計數同步變化
- 欄內排序符合到期日規則（無到期日排最後）
- console 無錯誤

## 範圍外（明確不做）

- 點卡片開 modal 編輯——回看板分頁做（見上方「互動」小節原因）
- 欄內拖曳重新排序（`sort_order`／`move` 端點）——固定規則排序即可，不需要使用者手動調整順序
- 「顯示已完成」開關狀態持久化——每次切分頁重置，不做
- 甘特分頁——獨立規格，不在本次範圍
